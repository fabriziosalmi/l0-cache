    fix(guard): protect HOME and user-data dirs from rm -rf, close quote-insertion bypass
    
    The destructive-command guard only covered system roots (/, /etc, /usr, …),
    so `rm -rf ~`, `rm -rf $HOME`, and `rm -rf ~/Documents` passed the guard and
    executed (a real incident). Extend the recursive force-remove check to also
    block:
    
    - the HOME resolved at runtime from the environment ($HOME / %USERPROFILE% /
      HOMEDRIVE+HOMEPATH), both the exact path and its `…/*` glob;
    - its first-level data folders (Documents, Desktop, Downloads, Pictures,
      Movies, Music, and the Linux XDG Videos/Public/Templates);
    - literal, un-expanded `~`, `$HOME`, `${HOME}`, `%USERPROFILE%` references
      that reach the bash -c re-scan without a shell expanding them first.
    
    Coverage is cross-OS: Linux (/home/<user>, XDG), macOS (/Users/<user>), and
    Windows (C:\Users\<user>, backslashes, drive letters, and the /c/Users form
    used by Git Bash / MSYS) all normalize to a common comparison form.
    
    The bash -c / sh -c re-scan now tokenizes the payload with a minimal
    quote-aware de-obfuscator (removing '…'/"…" quotes, honoring `\` escapes)
    before matching, so `bash -c 'r"m" -"r"f /etc'` recomposes to `rm -rf /etc`
    and is blocked; plain split_whitespace previously let it through.
    
    Home directories are injected via check_dangerous_command_with_homes so the
    regression tests simulate each OS layout deterministically without mutating
    the shared process environment. The guard stays a best-effort lint (no var
    expansion, command substitution, or symlink resolution) with the existing
    --no-guard / L0_CACHE_GUARD=0 opt-out.

Author: Fabrizio Salmi <fabrizio.salmi@gmail.com>

    feat: clean-success squelch — trim the tail on a signal-free zero exit
    
    On a clean exit (0) with no error/warning signal anywhere in the stream,
    the displayed tail is trimmed to half (floored at 5 lines): the middle of a
    clean build/test/install is progress noise and the agent rarely needs 30
    tail lines to confirm success. The head (command echo) is always kept and
    the final summary line always survives. Any error/warn/fail/exception/panic/
    traceback/fatal signal — or a non-zero exit — restores the full tail, so
    failures stay completely visible (mirrors the safety guarantee that the
    failure path is never squelched).
    
    On by default; opt out with `--no-squelch` or `squelch = false` in
    per-command config. The error-signal keyword set is now shared between the
    `--only-errors` filter and the squelch gate so the two can never disagree.
    
    Honesty fix: the truncation banner now reports the ACTUAL tail shown, not
    the configured cap — the runner returns the rendered `display_tail` and the
    banner prints it (`30 head + 15 tail`, never a fabricated `30 tail`).
    
    Tests: filter unit tests (has_error_signal, squelched_tail math, sticky
    error-signal tracking across the whole stream), runner tests (squelch trims
    clean success, backs off on a warning, never touches failures), and an
    integration test asserting both behaviour and banner honesty. The three
    auto-tuning e2e tests that assert the tuned tail CAP now pin `--no-squelch`
    so the squelch can't trim the displayed tail out from under their banner
    assertions.

      pattern) because the scan only saw the opaque outer argv. Now re-scans each
      segment of the shell `-c` payload. Also normalize rm paths so `/etc/`,
      `/etc//`, `/etc/.`, `/etc/*`, `/*` are caught (trailing-slash bypass).
    - --tail-error / failure backoff was inert: expand_tail ran after the stream
      had already evicted lines. Removed expand_tail; the buffer now retains
      max(tail, tail_error) (and enough for the threshold, capped) and trims to
      the right window at render based on exit code. Also fixes a latent silent
      gap below threshold when the tail wrapped.
    - --raw is now truly raw: progress-bar/backspace squashing and the >2000B
      JSON truncation are filtered-mode only; raw keeps content verbatim.
    - bytes_raw is measured from the true pre-transform byte count, so token
      savings are no longer understated.
